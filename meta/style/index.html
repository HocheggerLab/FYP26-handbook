    Writing style contract¶

    For whoever writes or edits these pages — including AI assistants, which default to comprehensive when teaching material needs to be sparse.

    The 2025 cohort was given PDFs of long markdown notes. The format was not the problem; the register was. Reference prose dressed as instruction serves nobody.

    Site structure — shared vs project¶

    docs/
  index.md              course landing; the four projects and what they share
  course/               everyone reads; must be project-neutral
  projects/<slug>/      one section per project, do/ lookup/ understand/ ...
  meta/                 this contract

    Two rules, and they are the ones most likely to be broken by an assistant adding "just one more page":

    1. Nothing in course/ may address a single student or name one project's fields. If a sentence only makes sense to the literature student, it belongs in projects/literature/. Cross-project examples are fine; second-person instructions to one student are not.
    2. Nothing in projects/ may restate a course/ page. Link to it. A project's marking page carries its weights only; the policy lives in course/how-you-are-marked.md.

    One repo, not one per project. The shared pages would drift within a term, and the whole design is a comparison between the projects — students need to be able to read across.

    Hard limits¶

    Section Limit
    do/ task cards 2 screens. If it doesn't fit, the task is too big — split it
    lookup/ pages 1 screen, or a table of any length
    understand/ pages 3 screens
    reference/ no limit; nobody reads these front to back

    The four registers, never mixed on one page¶

    • do/ — imperative, one sitting's work, gated by week.
    • lookup/ — terse, tabular, for glancing at mid-task.
    • understand/ — narrative, read once, explains why.
    • reference/ — the full spec, for settling a dispute.

    A student halfway through abstract 47 needs a one-page table, not paragraph six of section eight. That is the whole point of the split.

    Every task card has these six headings, in this order¶

    ## Goal
One sentence.

## Time
Realistic, not optimistic.

## Before you start
What must already be true.

## Steps
Numbered. Imperative. One action each.

## Done when
Explicit and checkable.

## If you get stuck
Three escalation steps, then email.

    "Done when" is not optional. The most common student question is not "how?" but "is this right, and can I move on?" — and verbose prose is silent on exactly that.

    Rules¶

    • Worked example before rule, never after. Nobody learns annotation from a rulebook. Show the JSON, then explain it.
    • Table over prose for anything enumerable.
    • No preamble. Delete "In this section we will…", "It is important to note that…", "As discussed above…".
    • Second person imperative. "Copy the span", not "the span should be copied".
    • One idea per numbered step. If a step has an "and" in it, split it.
    • Name the trap. Where students predictably go wrong, say so directly and say what to do instead.
    • No hedging. If something is genuinely uncertain, say what to do about the uncertainty.

    When you change a page¶

    Anything a student may have already acted on — the schema, the corpus, the annotation rules — gets a dated line in the changelog at the bottom of that page. Silent edits break the audit trail that the frozen corpus_version and schema_version exist to provide.
