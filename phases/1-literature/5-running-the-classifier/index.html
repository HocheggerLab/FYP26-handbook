    Part 5 · Running the classifier¶

    Goal¶

    Run the Jev classifier over the same 50 abstracts you classified by hand, so that in Part 6 you can measure how well it agreed with you.

    You will learn the tool by interrogating it with the agent, then run it yourself from the terminal. Both halves matter: the agent is there to explain, not to press the button for you.

    Time¶

    About two hours, most of it understanding the tool rather than running it. Evaluation runs happen during 17–24 November, after the independent references are locked.

    Before you start¶

    • Part 4 finished: VS Code, uv and Claude Code working.
    • Your abstract classifications submitted. Do not run the classifier before your own answers are locked. Seeing the model's answers first contaminates the reference you are measuring it against, and there is then nothing left to compare.
    • The .env file your supervisor sent you by Slack DM. It already contains the key; you only have to save it in the right folder.

    Steps¶

    1. Get the tools¶

    git clone https://github.com/Helfrid/fyp26-tools
cd fyp26-tools
uv sync --all-packages

    This folder holds the scanner, the 250 abstracts assigned across the group (input_data/), and everyone's hand classifications (abstracts_annotated/).

    2. Put the key in place¶

    Your supervisor sends you a file called .env by Slack DM. It already contains the API key. Save it into the fyp26-tools folder — the same folder as README.md — without opening or editing it.

    That is the whole step. The scanner looks for .env in the folder you run it from and reads the key out of it.

    Keep the key out of everything else

    Do not paste the key into the Claude Code chat, into a notebook, or into a results file. Everything typed in an agent session is written to a transcript file on your computer, including ! shell commands.

    Never commit .env. It is gitignored, and a pre-commit check will refuse a commit that contains a key. If you think the key has leaked anywhere, say so immediately — it can be rotated in a minute, and no one will mind.

    3. What kind of software is this?¶

    fyp26-tools is a collection of command-line apps. There is no window and nothing to click: you type a command in the terminal, it does one job, and it prints the result or writes a file. Your agent runs them the same way you do, by typing the same commands.

    Start Claude Code in the fyp26-tools folder:

    claude

    Every command-line app will tell you what it can do if you ask it:

    uv run abstract-scanner --help

    Four commands: guide, validate, estimate, scan. Now run the first one:

    uv run abstract-scanner guide

    What you are reading is unusual and worth a moment. It is not a manual for you — it is instructions written for an AI agent, shipped inside the app, telling it how to run a scan on a student's behalf: ask what they are looking for, draft the questions, check back with the student before spending anything, validate, price it, trial a few, then run the full scan.

    This is the same idea as the skills and CLAUDE.md from the agent session. The tool carries its own instructions, so any agent that picks it up behaves the same way. You will use that properly in Phase 2, when you design your own question set for the phosphatase literature. Today the question set is already written for you, because it has to match what you did by hand.

    4. What you need to understand for your report¶

    You are not expected to read the Python. You are expected to be able to say what the thing you ran actually did. That is a methods section, and a viva question.

    Three parts go in, two come out:

    flowchart LR
  A["input_data/<br>250 abstracts<br>(title + abstract)"] --> S
  Q["question_sets/<br>4 typed questions"] --> S
  K[".env<br>API key"] --> S
  S["abstract-scanner<br>one request per abstract"] <--> J["Jev<br>(the classifier,<br>on a server)"]
  S --> R["results/*.jsonl<br>one line per abstract"]
  S --> M["results/*.manifest.json<br>what was run, and what it cost"]

    Read in order, that is the whole story:

    1. The abstracts. Only the title and abstract of each paper are sent. Not the journal, not the authors, not the year — so the model cannot be swayed by a famous name or a glamorous journal, and neither were you.
    2. The questions. Four of them, each with a declared type and a fixed set of options. The same four fields you filled in by hand, in the same words.
    3. The key. Identifies the lab's account, so the usage is billed and capped.
    4. The scanner. Runs on your laptop. It reads the abstracts one at a time, sends each one with all four questions, counts what it has spent, and stops if it reaches your ceiling. It never decides anything itself.
    5. Jev. Runs on someone else's server. It answers each question independently — question two does not know what question one decided — and returns a probability for every option rather than a single verdict.
    6. The results. One line of JSON per abstract, written as it goes, so a crash halfway through loses nothing.
    7. The manifest. What was asked, which model version answered, how many abstracts, how many tokens, what it cost. Without it a results file is just numbers of unknown origin.

    The five words worth being able to define: corpus (the abstracts), question set (what is asked), typed answer (an answer forced into a declared shape), budget (a hard ceiling in dollars), manifest (the record of what was run).

    5. Your first task: explain it in your own words¶

    Explore the repository with the agent until you can describe it yourself. Prompts that work:

    • "Read the README and CLAUDE.md and explain in plain language what this repository does."
    • "Show me question_sets/fyp26_tagging_v3.toml and explain how it relates to the four fields I classified by hand."
    • "Walk me through what happens to one abstract, from the input file to the results file."
    • "What exactly is sent over the internet for each abstract, and what is not?"
    • "Explain every flag on the scan command. What does --budget do, and what happens when it runs out?"

    Then close the chat and write one paragraph, in your own words, saying what the app does and what it does not do. Not copied from the agent, not pasted from the README — yours, roughly 100–150 words, in your report notes.

    How to know whether the paragraph is good enough

    Show it to the agent afterwards and ask it to point out anything you have got wrong or left out. Fix what is genuinely wrong. Do not let it rewrite your paragraph into its own prose: a paragraph that sounds like an AI wrote it will be read as one.

    Then ask the agent for the exact commands for the three steps below — and check them against this page before running anything. If the agent's command differs from the one here, this page wins. Ask it why they differ; it is a good test of whether you understand the tool.

    Do not let the agent change the question set

    fyp26_tagging_v3.toml must stay exactly as it is. It encodes the same four fields and the same wording that you classified by hand. If a single instruction is reworded the file's fingerprint changes, your run can no longer be compared with anyone else's, and your result drops out of the group analysis. If the agent offers to improve it, decline.

    6. Check the question set — costs nothing¶

    uv run abstract-scanner validate -q packages/abstract_scanner/question_sets/fyp26_tagging_v3.toml

    You should see four questions and a fingerprint. Note the fingerprint down; it identifies exactly what was asked.

    7. Price the run — costs nothing¶

    uv run abstract-scanner estimate \
  -a input_data/phase1_tagging_abstracts.json \
  -q packages/abstract_scanner/question_sets/fyp26_tagging_v3.toml

    Nothing is sent and nothing is charged. Read the number before you spend it. The whole set of 250 abstracts costs roughly one US cent.

    8. Run the scan¶

    uv run abstract-scanner scan \
  -a input_data/phase1_tagging_abstracts.json \
  -q packages/abstract_scanner/question_sets/fyp26_tagging_v3.toml \
  -o results/jev_tagging_v3.jsonl \
  --budget 0.05 \
  --cache .cache

    What the flags mean:

    Flag Meaning
    -a the abstracts to read in
    -q the questions to ask about each one
    -o where the answers are written out
    --budget a hard spending ceiling in US dollars. Required — there is no default
    --cache remembers answers, so running again costs nothing

    If it stops at the budget it says so, keeps everything it finished, and exits with code 2. Raise --budget and run the identical command again; it picks up where it left off.

    9. Look at what came back¶

    Open results/jev_tagging_v3.jsonl. One line per abstract, each a JSON object with the four answers. For every question you get the chosen option, a confidence, and the full probability distribution across the options — more than you produced by hand, and useful later.

    Open results/jev_tagging_v3.manifest.json too. It records the question fingerprint, the model version, how many abstracts were scanned, the tokens used and the actual cost. Keep the two files together: without the manifest you cannot say what a result file actually is.

    10. Log it¶

    Add a line to ai-use-log.md: what you asked the agent, what it told you, and anything you had to correct. If the agent gave you a command that was wrong or that you chose not to run, that is worth recording — it is evidence of the judgement the project is assessing.

    Done when¶

    • A paragraph in your own words, in your report notes, saying what the app does and what it does not do.
    • results/jev_tagging_v3.jsonl has one line per abstract.
    • You can explain, without looking it up, what -q, -o and --budget do.
    • You can say what the fingerprint is for, and why the question set must not be edited.
    • ai-use-log.md has an entry.

    If something goes wrong¶

    The classifier fails loudly rather than silently. Read the error, then ask the agent what it means — debugging with the agent is exactly the right use of it.

    What you see Usually means
    no API key: set TYPESAFE_API_KEY .env is not in the fyp26-tools folder, or was saved as .env.txt
    ✗ every record failed the request was rejected; read the first error printed underneath
    stopped at the budget ceiling not an error. Raise --budget, run the same command again
    no such corpus file you are not in the fyp26-tools folder, or the path is mistyped
